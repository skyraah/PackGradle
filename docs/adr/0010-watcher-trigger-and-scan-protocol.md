# 0010 · watcher 触发面与增量扫描协议

决策图 #70 票 [#73](https://github.com/skyraah/PackGradle/issues/73) 的产物。锚点：ADR-0005 §3 已定 watcher 定位=「非冲突自动物化，上游变更自动同步的终态形态」、§1 定双向受管；契约 04 已定型事件面（`relation_invalidated` / `watch_failed` 预留 / 受控重查管线）；legacy `internal/service/mods_watch.go` 冻结实现仅作参考不迁移。本 ADR 决策化：触发后端语义与编排落点、监听面与生命周期、静默期聚合、失败防打转、错误面降级、增量扫描协议 v1 边界。术语「监听」「自动快速更新」见 CONTEXT.md。

## 1. 触发语义：自动快速更新（终态一步到位）

watcher 察觉变化后的后端动作=**自动快速更新**：走与手动入口完全相同的编排链（扫描 → PrepareSync → ResolvePlan → 免确认口径判定 → ConfirmPlan），不存在「只扫描不物化」的半态。触发谓词=**扫描后存在差异**才继续；apply 写盘引发的再次触发经收敛扫描（无差异）自然终止，自触发循环有界。

- 授权模式开启 ∧ 计划 `confirmation_requirements` 为空 → 自动执行（免确认唯一口径，与手动一致）。
- 授权模式关闭、或 requirements 非空（删除/不可恢复等损失面）、或含冲突 → **停为待确认计划**（计划页既有流；用户不处理则下轮触发自然重现）。
- 冲突与删除永不自动（ADR-0005 §4 红线不动）；恢复所需期间触发只标脏不自动物化（见 §4）。

## 2. 编排落点：统一后端用例

快速更新整体下沉为**一个后端用例**：链路与免确认唯一口径单点住在后端，前端一键入口改为调用该用例（导航与提示仍在前端），watcher 触发走同一用例。

- 现状是纯前端编排（契约 06 §4「零新方法」），窗口关闭时前端不在场，而常驻监听（§4）要求窗口外也能自动同步——后端编排是必然推论。
- 口径两处实现必然漂移，故手动入口一并收编，不保留双编排。
- 契约 06 §4 的「零新方法」为 P3 语境（当时无自动面），本决议局部推翻；新方法与 wire 形状入契约 07（票 [#75](https://github.com/skyraah/PackGradle/issues/75)）。

## 3. 监听面：双端 × policy 管辖目录

监听对象=**双端**（上游变更与运行端手改都要察觉，ADR-0005 §1 双向受管）× **MappingPolicy 管辖的语义资源目录**：

- 项目侧：`pack.toml` + mods + config / kubejs / scripts / defaultconfigs（default-v1 模板涉及的目录）。
- 运行侧：`minecraft/` 下同名管辖目录。
- 排除：logs、saves 等非管辖树；Prism 自有元数据（mmc-pack.json 在 runtime root 之外，ADR-0005 §6 只提示）；`mods/.index`（§5 只读不写，Prism 事后自行重写只产噪声，其变化由 mods 文件变化本身反映）。
- 监听面是 policy 的函数：policy 修改 → 重挂监听；递归新子目录由目录创建事件动态补挂。

## 4. 生命周期：常驻

应用运行期间对**全部健康 relation 常驻监听**（窗口开闭无关——窗口关着时上游变更静默漏掉正是终态要消化的场景）；relation 建立/重绑/删除 → 动态挂卸。恢复所需期间挂载保持、触发只标脏不自动物化（与授权模式恢复暂停同型；禁新 Apply 既有约束兜底）。fsnotify 单 watcher 多目录（legacy 同型），规模=relation 数 × 管辖目录数，桌面规模无压力。

## 5. 聚合：静默期 + 单飞

- **静默期触发**：无新事件持续 1.5s 才触发，另设 10s 最大等待强制触发（常数施工可调）。git 拉取/切分支一次写几百文件超固定窗口会切刀产生中间态扫描，静默期+上限优于 legacy 的 600ms 固定窗口。
- **进行中再失效**：inflight 单飞 + 新失效只标 dirty + 本轮结束后补一轮至干净——与受控重查（契约 04 §2.4）同型，风暴最多两轮。
- 任务互斥沿用既有守卫（StartScan 创建段互斥、ConfirmPlan 的 apply_runs 跨计划互斥），自动链不绕过、不插队；多 relation 并存各自独立链路，无全局串行。

## 6. 失败防打转：连败计数 + 暂停

事实：apply 失败回滚时**回滚自身的写盘会产生 watcher 事件**——重扫 → 差异仍在（上游变更未消化）→ 新计划 → 再自动执行 → 再失败，「无新事件不重触发」的天然防护在回滚路径上不成立，存在无限重试循环。

决议：同一 relation 自动物化**连续失败 2 次即暂停该关系自动面**（监听保持、视图标脏 + 一次性提示）；用户手动快速更新成功后自动复位。不做定时重试/指数退避（引入新常量面，且持续故障变成周期性空转）；恢复所需由既有禁新 Apply 兜底。2 次容得下偶发抖动（下载瞬时不可达），又不让持续性故障空转 IO。

## 7. 错误面：分桶 + 降级手动

- **目录暂时消失** → 回退注册最近存在的父目录（legacy 验证过的手段），目录再现由父监听捕获重挂。
- **权限 / 句柄耗尽 / watcher 异常** → 自动重建（有限次数）→ 仍败发 `watch_failed`（契约 04 §2.5 预留语义：按 invalidation 处理 + 一次性「监听不可用」提示）。
- **降级=回手动**：快速更新可用性完全不受监听死亡影响。watcher 是加速器不是正确性来源——正确性锚=手动快速更新 + 前端 30s 周期对账（只刷视图）。
- 后端**不做**周期重扫对账（无人要求的常驻 IO 成本）。

## 8. 增量扫描协议：v1 不做

维持**全枚举 + hash cache**（键=RootFingerprint + 路径 + size + mtime + filekey，未变文件已免重哈希，每文件成本 stat 级）；增量枚举协议（快照差分 / mtime 剪枝 walk）不做。理由：静默期聚合已把触发频率压到用户操作级；3000 文件级包的 stat 遍历为百毫秒级；复杂度预算应花在 merge/watcher 正确性上。L1 走查 / `-metrics` 实测若暴露瓶颈再回图另议（与 #69「先测后修」同款逻辑）。

## 9. 事件面：零新事件类型

watcher **不是**新事件生产者：自动链的效果经既有 `task_updated`（链内任务）与 `relation_invalidated`（扫描提交后既有发点）到达前端，走契约 04 受控重查管线；`watch_failed` 沿契约 04 预留常量启用。边界篇「Phase 4 watcher（仅发 relation_invalidated）」锚细化为「watcher 不新增事件类型、自身不直接发事件」。

## 10. 选型：fsnotify

事实标准、legacy 已用（冻结树已验证 Windows 行为）、watcher 属 adapters 层实现、core 不 import fsnotify（边界篇 §4 不破）。无候选竞争，不单开调研。
